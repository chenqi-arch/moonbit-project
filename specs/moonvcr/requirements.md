# MoonVCR 需求规格

状态：阶段 2（需求与申报结构）已确认

项目名称：`MoonVCR：MoonBit HTTP 交互录制回放与离线契约测试库`

项目定位：MoonBit 的 HTTP 交互录制、回放与离线契约测试库。它把一次经过允许的真实请求保存为可审阅的 cassette，随后在开发和 CI 中不访问网络地重放，并在请求不匹配时给出结构化差异。

## 1. 背景与目标

许多 SDK 和服务端程序依赖第三方 HTTP API。现有测试往往需要真实凭据、稳定网络和可重复的服务状态，导致测试慢、昂贵、易受限流影响，也很难在无网络 CI 中复现。

MoonVCR 的目标是提供一套 MoonBit 优先、可审阅、默认保护敏感信息的录制/回放核心，让调用方以最小适配代码获得确定性的离线测试。当前对 Mooncakes 注册表的类别检索未发现直接同类的 `VCR/cassette/record-replay/http mock` 模块；这不是对全世界项目“不重复”的绝对保证，最终仍需在建仓和提交前再次核验。

## 2. 范围

### 2.1 MVP 必须包含

1. 类型化的请求、响应和交互记录模型。
2. 稳定 JSON cassette 格式：字段顺序、换行和数组顺序可确定，方便 Git review。
3. 可组合的请求匹配器：HTTP 方法、规范化 URL/查询参数、选定请求头、请求体摘要或内容。
4. 明确的 `record`、`replay` 和严格离线模式；回放未命中时返回类型化错误，不能暗中发起真实请求。
5. 默认敏感信息清理：至少覆盖 `Authorization`、`Cookie`、常见 API key 头/查询参数，并允许调用方声明 JSON 字段路径。
6. 结构化 mismatch 诊断：指出方法、URL、头、体或序号等差异，而不是只返回一条字符串错误。
7. transport-independent 适配接口，使 MoonBit HTTP 客户端可以接入而不要求透明代理。
8. 一个可直接运行的第三方 API 离线示例，以及无需网络即可运行的核心测试。

### 2.2 明确不做

- TLS MITM、系统级代理或自动拦截任意进程流量。
- 依赖外部服务才能通过的测试；真实 API 仅用于开发者主动录制示例 cassette。
- 在截止日前扩展成完整 API 测试平台、浏览器录制器、分布式 cassette 服务或复杂模板语言。
- 机械移植其他语言的 VCR 源码；实现、数据结构和 MoonBit API 由本项目重新设计。

## 3. 目标使用者与完整场景

### 场景 A：第三方 SDK 的单元测试

SDK 作者在一次有凭据的录制阶段访问地图、支付或 OCR 沙盒接口，提交脱敏后的 cassette。之后每次本地测试和 CI 都通过回放验证参数编码、错误处理和响应解析，不需要凭据或外网。

### 场景 B：受限流或不稳定供应商的回归测试

业务服务依赖有调用配额的供应商 API。开发者录制代表性成功、鉴权失败和限流响应，测试在 `replay` 模式固定复现这些分支，避免重复消耗配额，也避免供应商临时故障阻塞发布。

### 场景 C：内部 HTTP 服务的契约回归

服务团队将旧版本交互保存为 cassette。在接口升级后，回放同一请求并查看结构化差异，快速发现状态码、响应头或 JSON 响应结构变化；任何未登记的新请求在严格离线模式下直接失败。

### 场景 D：无网络教学与示例复现

开源项目把示例 cassette 和测试一起发布，贡献者只需安装 MoonBit 工具链即可运行完整示例，降低新贡献者的环境门槛。

## 4. 功能需求（EARS）

### FR-01 交互模型

系统应提供可序列化的 `Request`、`Response` 和 `Interaction` 类型，至少保存方法、URL、请求头、请求体、状态码、响应头和响应体；二进制或不可打印内容必须有明确编码策略。

### FR-02 确定性 cassette

当系统写入同一组交互时，系统应生成字节级稳定的 JSON 表示；重新读取后再写入不应产生无意义 diff。

### FR-03 规范化与匹配

当调用方配置了匹配策略时，系统应按方法、规范化 URL/查询参数、选定头和请求体策略逐项匹配；未配置的可变字段不能被隐式当作必须相等。

### FR-04 严格回放

当处于 `replay` 或严格离线模式且没有匹配交互时，系统必须返回包含候选记录和差异字段的类型化错误，并且不得调用底层网络传输。

### FR-05 录制

当处于 `record` 模式且底层适配器成功返回时，系统应保存请求和响应的完整核心信息，并在落盘前应用清理策略。

### FR-06 敏感信息清理

当 cassette 即将落盘时，系统应默认移除或替换 `Authorization`、`Cookie` 和常见 API key；调用方显式加入的 JSON 路径也必须被清理。清理结果应可在测试中断言。

### FR-07 差异诊断

当请求与现有 cassette 不匹配时，系统应至少区分方法、URL、查询参数、请求头、请求体和交互序号差异，并提供可读摘要。

### FR-08 适配边界

系统应定义小而稳定的 transport adapter 接口；核心匹配、存储、清理和诊断逻辑不得依赖某一个具体 HTTP 客户端。

### FR-09 示例与测试

系统应提供一个不需要网络的 `replay` 示例、一个明确标注需要主动录制的 `record` 示例，以及覆盖成功、未命中、清理和确定性序列化的核心测试。

## 5. 非功能需求

- 可复现：默认回放路径必须在无网络环境中运行。
- 安全：不把真实凭据写入示例、测试输出或仓库；README 明确录制前的凭据检查。
- 可维护：核心 API、cassette schema、错误类型和匹配规则有文档与测试。
- 可移植：优先使用 MoonBit 标准能力；平台相关代码限制在适配层，并记录已验证目标。
- 可审阅：每个 cassette 都是普通文本，变更可被 Git 逐行检查。
- 合规：采用 OSI 认可许可证；若借鉴成熟 VCR 概念而不复制代码，在 README 中明确“概念参考”和本项目原创实现边界。

## 7. 有意义的提交里程碑（不是拆分提交凑数）

提交应以可运行、可测试的独立功能为单位，预计至少包含以下 11 个里程碑：

1. 项目骨架、许可证、基础 CI 与最小可运行测试。
2. 请求/响应/交互模型与错误类型。
3. cassette schema、JSON 编解码和确定性输出测试。
4. URL、查询参数和头的规范化工具。
5. 可组合请求匹配器与候选选择规则。
6. record/replay 引擎与严格离线拒绝网络逻辑。
7. 默认敏感信息清理及自定义字段路径。
8. 结构化 mismatch 差异报告。
9. HTTP transport adapter 与最小端到端示例。
10. 核心测试矩阵、脱敏 fixture 和无网络 CI 验证。
11. README、Mooncakes 元数据、发布检查和最终示例完善。

每个里程碑都必须改变源代码、测试、文档或可验证配置，并在提交信息中说明用户可见结果；禁止空提交、重复提交或事后改写历史。
