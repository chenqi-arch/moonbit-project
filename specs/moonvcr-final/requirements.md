## 当前基线

2026-09-21 本地提交 236608d，版本 0.2.0，22 条提交。检查开始时跟踪文件干净；本轮 moon test 实测 59 项通过、0 项失败。已具备档案编解码、请求匹配、会话、脱敏、轻量响应契约、脚本 transport、离线 demo、许可证及 CI。

## 目标

开发者首次通过真实 HTTP 接口录制获准使用的数据，脱敏保存；停止服务后，新进程加载档案，以同一业务调用流程离线测试；请求或响应违约时，给出可定位错误并阻止 CI 通过。

每个功能都必须对应可运行例子、正反测试和验收证据。P0 是阻断最终发布的问题；P1 是本轮计划内的实用性增强，不是任意堆功能。

## R1 / P0：匹配正确性

发现：normalize.mbt 用 name=value 和 & 拼接请求头。一个头 a: b&c=d 与两个头 a: b、c: d 可生成相同文本；matcher.mbt 用该键判等。

方案：改为无歧义结构化表示或长度编码。定义查询重复项、空值、重复头、大小写、分隔符、Unicode、body 的匹配规则；有意义的顺序不默认抹除，宽松策略显式配置。保留旧档案回归。

验收：当两个请求结构不同但旧键相同时，必须区分；重复请求正确消费；正反例覆盖上述边界；缺陷用例修复前失败、修复后通过。

## R2 / P0：脱敏与错误输出

发现：ReplayMiss 携带完整 MatchCandidate.key，包括参与匹配的头和 body；安全 summary 不覆盖所有错误输出。诊断保留 URL 基址；脱敏保留片段，查询名未做百分号解码识别；请求和响应共用 JSON 路径。上述静态发现需先写复现测试。

方案：内部匹配数据与公开错误分离；默认错误和调试输出不暴露原文键。明确 URL 用户信息、片段和编码敏感参数处理。分离请求/响应路径，区分必需和可选规则；规则无效失败关闭。审查短非加密指纹，不能把指纹当作保密保证。

验收：编码 token、URL 用户信息、片段、非对称请求/响应 JSON、数组、非法路径和非 JSON body 均有用例；植入的敏感值不出现在保存档案及公开错误日志；必需规则处理失败不追加记录。明确未知业务敏感字段仍需配置，以及脱敏对回放数据和身份匹配的影响。

## R3 / P0：会话状态完整性

发现：Session 持有可变数组，cassette() 返回内部档案，消费状态单独保存；外部修改的隔离性需测试。Replay 和 StrictOffline 当前行为相同。

方案：测试并隔离外部对档案、响应及配置的修改，采用快照或受控访问；增加已消费/未消费统计与完成断言。保留离线模式兼容语义；若加入全局严格顺序，必须与重复请求顺序分开配置。

验收：外部修改不造成越界或改变既定回放；失败不误消费；多调用、少调用、重复项耗尽均能发现；不同会话独立。

## R4 / P0：真实 HTTP 接入和平台验证

发现：当前发送接口为同步函数；脚本 transport 不发 HTTP。官方异步库当前声明 Linux/macOS native/LLVM 支持且 API 实验性，不能直接承诺 Windows 可用。

方案：先做工具链、后端和具体依赖版本探针。优先实现官方 HTTP 库的独立适配包，核心保持无 IO。异步入口或显式录制接口需设计错误、取消和顺序语义。Linux CI 验证官方适配；Windows 用 JS/Node 最小 IO 桥接路线做可行性探针，业务逻辑仍用 MoonBit。设计阶段冻结支持矩阵，未实测不宣传。

验收：本地真实服务完成 GET、POST、头、JSON、字节 body；连接失败、超时、非 2xx、空响应有明确行为；录制和回放结果符合脱敏规则。定义并验证超时、响应大小、重定向和 TLS 边界；不关闭证书验证以通过测试。

## R5 / P0：档案文件读写

方案：独立 IO 层提供加载、保存；默认拒绝覆盖已有文件，显式更新才允许替换。使用同目录临时文件和平台支持的安全替换；限制大小和交互数；清楚区分文件及格式错误。格式变化须提供迁移或明确拒绝。

验收：进程 A 录制保存，进程 B 加载回放；不存在、权限不足、截断 JSON、未知版本、过大输入明确失败；失败保存不损坏旧文件；最终文件不含测试凭据。分别验证支持的 Windows/Linux 路线。

## R6 / P1：契约实用性

方案：在状态码、响应头存在性、body 类型、JSON 字段类型基础上，加入必要头值/媒体类型、可选字段及数组元素规则；提供测试断言范例，错误配置提前报告。保持小型确定性规则，不扩张为完整 JSON Schema。

验收：正确订单通过；id 数字变字符串、必需字段消失、数组单项类型错误、Content-Type 错误分别定位；可选字段缺失通过、存在但错误失败；摘要稳定且不带业务原文。仅检查传入/回放响应，不宣称自动监测未录制的线上变化。

## R7 / P0：三个完整场景及失败退出

方案：交付录制、回放、检查入口和三个可运行场景：分页 SDK 回归、订单响应兼容检查、受限网络 CI。每个提供输入、代码、档案、成功输出及故障输出。修复 demo 失败仅打印后返回的问题，自动验收失败必须非零退出。

验收：启动服务→SDK 请求→脱敏保存→停止服务→新进程加载→同一 SDK 离线回放→业务断言和契约通过。修改请求、删除字段、少执行一次调用应分别失败；额外断言离线 transport 调用为零，不能只靠服务停止证明。

## R8 / P0：可靠性及 CI

方案：保留回归，增加每项缺口的反例、状态测试、固定种子生成测试和真实 IO 集成测试；移除重复打包步骤；固定验收工具链及依赖，另设升级兼容检查；自动运行 README 完整例子。记录提交 SHA、工具链、后端、命令和结果。

容量检查：对 100/1000/10000 条档案测耗时和资源，实测后给容量建议，发现瓶颈再优化；不编造性能保证。

验收：所有声明支持的平台通过检查、构建、格式、单元/集成/消费测试；故意制造错误时 CI 红灯；没有未解释的崩溃。需求逐项映射测试与结果，不以测试数量代替质量。

## R9 / P0：文档及开源完整性

方案：README 包含价值、安装、完整快速开始、三个场景、支持平台、输入输出、错误排查、API 及限制；提供变更日志、迁移说明、贡献说明和安全边界。核查根许可证、版权及新增依赖/借用代码的来源、许可证和署名，按实际义务保留第三方声明。仅使用合成示例数据。

验收：干净目录按说明可操作，无伪代码冒充完整示例；名称、版本、GitHub、Mooncakes 和最终材料一致；依赖许可可追踪，包中不含个人联系方式和原始凭据。

## R10 / P0：最终发布证据

方案：独立完成的工作单元正常提交并同步 GitHub，解释修改目的与测试；不改写历史或凑提交数。全部验收通过再确定版本、标签、正式包；独立消费者安装正式包运行例子。更新验收矩阵和简明终审使用说明。

验收：冻结提交、CI、标签和包内容对应；P0/P1 完成或经用户明确调整，无已知严重缺陷；最终材料仅描述实测能力；留一轮完整预演及修复时间，冻结后不追加无关功能。

## 执行顺序

1. A：匹配、安全输出、脱敏、状态问题复现与修复。
2. B：平台/异步探针，确定设计，再实施真实 HTTP 与文件 IO。
3. C：契约增强、三个业务场景、成功与故障流程。
4. D：CI、异常及容量验证、文档和开源核查。
5. E：版本冻结、独立消费、终审预演及发布证据。

每批报告交付、测试、未解决问题和提交。用户确认范围后进入设计和任务拆分，不把计划标成完成。
